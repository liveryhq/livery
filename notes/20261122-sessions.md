How a session was made there:

- **A name for a subsystem, and the packages it owns.** The `core` brief:
  "In packages: `scanner_engine`, `scanner_agent`, `scanner_config` ...".
- **One worktree each**, never the main checkout.
- **A track-state file in the agent's memory**, with a PARKED block when
  the session stops.
- **A startup brief the orchestrator writes by hand**, 200 to 300 lines,
  with the same sections each time: Willem's words verbatim, your
  responsibility, what you take over, first jobs, standing holds, rules
  that bite, unclear so ask the orchestrator, how to report.

never merge; you land), and order deploys through link."

What that cost, as the briefs show: the memory index sat at its byte limit
(24,985), every restart needed a hand-written brief because the state was

## The principles

1. **A session owns packages, and its edge is a package's public
   interface.** It reads its own packages whole and the others' public
   names only. This is the rule against reaching into privates, applied to
   context.
2. **Few sessions, and at most four working at once.** That is where
   humain-scanner ended after sixteen.
3. **What a session needs to know is in the repository.** Its definition,
   its guidance and its state. A second person's session with the same
   name then starts from the same knowledge, which an agent's memory
   cannot give.
4. **A session can be cleared and started again from its definition.** Its
   state is the plan note's status, its open pull requests and the queue.
   Nobody writes a startup brief.
5. **The orchestrator holds no build knowledge.** The train, the heavy-job
   slot and the relaying of decisions are the tools' work once the single
   plan is built: the queue lands, a lock holds the slot, rulings are in
   the notes.

No session runs the queue. It lands and drops entries from CI, with no
agent running. `workflow` owns its code. The orchestrator reads it, as a
person would.

Auditing a finished phase is not a session and not a kind of agent. It
is the `phase-audit` skill, which the claude extension already ships: any
session calls it, runs each acceptance command again, and appends the
evidence to the plan note's decision record. The orchestrator calls it
for a phase another session built, so the session that judges the
contracts is not the one that wrote the code.

Deep reading and measuring, as the review of 2026-11-22 used, are agents
a session starts for one question and that return a report to it.

Running `fm ci.e2e` is not a session either. Only one pass may run on a
computer at a time, and that is a lock the tool holds. The loop's code
belongs to `ci` until the lodge exists.

Working sessions during the single plan, by its order: `gate` for the
record and the metrics row, `ci` and `forge` for the CI model and the
identities, `forge` for the forge facts, `engine` and `gate` for the one
spelling and the item graph, `workflow` for the queue. `footman` joins for
the hook that lets an extension replace a verb. `stores` joins for a
series a person's session may write.

What this set does not cover:

- **A change that crosses two areas.** One session takes it, and the other
  area's part is limited to its public names, or the orchestrator splits
  the issue.
- **The docs site.** Each change updates its own docs, by the rule that a
  note or a page changes with the code. The site's own code belongs to
  `engine`, with the docs extension.
- **Sizes are uneven.** `footman` and `engine` are the largest. `engine`
  splits into the engine and the extensions if it proves too large.

## Several people

A session's name is a role, not a single holder. Two people can each have
a `forge` session open, and each an `orchestrator`. What keeps that safe
exists or is in the single plan, and none of it is a rule about sessions:

- an issue is assigned to one account, and the forge shows it;
- each stream has its own branch and worktree;
- the queue lands changes in order and drops a conflicting one by name;
- the affected engine can show two streams in one area before either
  submits;
- a ruling is in a note's decision record, so both people's sessions read
  the same one. An agent's memory is one account's alone.

A session is addressed by its name and its person, since the name alone
is no longer unique. The person is their account on the repository's
forge, for three reasons:

- it is the one identity every party can check, because every message
  travels through the forge and the forge says who wrote it;
- it is the same on every computer the person uses, and under every agent
  tool, so a developer with a Claude account on one computer and another
  agent on a second is still one person;
- the contract's `[owners]` table already names forge accounts, so "whose
  word decides" and "who is addressed" use one name.

The agent tool's own account is never part of an address. A session
learns its own address from its definition (the name) and from the forge
token in its environment (the account).

A person with the same session open on two computers has one address for
both. Either may answer, and the answer is on the forge, so the other
reads it. The computer a stream runs on can be shown beside it. It is not
part of the address.

The case Willem has in practice: he works on an Unreal project, which is
built on a desk and not in CI, with an editor open on a Mac and on a
Windows computer, and now and then tells the Windows session to take the
latest, build, test and fix what differs there. And a computer can matter
for itself, not for its platform: "Sometimes it really is a specific
computer that contains or is attached to particular hardware."

So an address has a third part when it is needed: the session's name, the
person's forge account, and the computer. A request can name the computer
that has the hardware, or leave it out and reach the person's session
wherever it runs. The computer's name is one its person gives it. A
computer nobody named cannot be addressed, which is the ordinary case.

A proof still comes from CI alone. Willem ruled out a second kind of
runner on 2026-11-22: a person's computer does not write a platform's
verdict into the shared record. A project that needs a platform proved is
made buildable in CI. The session on the other computer builds, tests and
fixes, and its fix travels on the branch through origin, as any change.

One thing is single: the main orchestrator. On humain-scanner, in
Willem's words, it "was the one who held and managed the grants ledger,
and synchronized actions and distributed plans between their relevant
sessions". So it is a role with work of its own, and exactly one holder at
a time. Each of its three duties, as this design carries it. Mine, not
ruled.

- **Holding the ledger** stops being a duty. The ledger is a shared record
  that every contender reads, not something in one session's context.
- **Managing the ledger** stays, and is why the role is single. A grant
  that needs judgement, such as which grants belong together, is decided
  by one holder. Two deciders would grant against each other.
- **Synchronising actions** is a request addressed to a session, through
  the forge, which the session reads as a notice.
- **Distributing plans** is the plan note in the repository, with each
  phase naming the paths it touches. A session's owned paths say which
  phases concern it, so nobody writes a brief per session.

Knowing and changing who holds it:

- **Two facts, kept apart.** Who may hold the role is the contract's
  `[owners]` table, changed by review. Who holds it now is one line in the
  shared record: the account, since when, and who set it.
- **A handover is an act of the holder or of an owner**, and takes effect
  when the line is written. It moves no state, because the ledger and the
  plans are not in the holder's context. On humain-scanner a new
  orchestrator needed a startup brief of 207 lines.
- **The holder is an account, not one running session.** A session can end
  and start again without a handover. If the holder has the orchestrator
  open on two computers, both may decide, and the ledger's own
  compare-and-swap keeps two grants from crossing.

What that does not cover: a repository with no ledger. There the role
still decides which work comes first and answers a request that needs a
ruling, and that is all.

## Declaring them in a repository

A session's definition is a fact of the workspace, so it belongs with the
workspace's other facts, and an agent tool's own files are rendered from
it. That keeps the definition free of any one agent, as the default
project list is.

What a definition holds, taken from humain-scanner's brief and cut to
what a tool cannot know by itself:

- its name and one sentence of responsibility;
- the paths it owns;
- the guidance it loads beyond the shared rules;
- what it decides alone and what it asks;
- whom it reports to.

What the brief held that a definition leaves out, because a tool reads
it: what you take over (the plan note, the open pull requests), standing
holds (the queue and the locks), and how to report (the forge).

What exists to build on:

- `fm start --agent=<name>` already starts an agent in a worktree with a
  briefing (`packages/workshop/src/livery/workshop/_issue_tasks.py:646`).
- A guidance fragment already has an audience in its file name,
  `<section>.<topic>[.<audience>].md`, and the audiences are `agent` and
  `human` today (`_prose.py:123`). A session's own guidance fits that
  shape.
- The claude extension already renders skills, hooks and settings into
  `.claude/`.
- A package's contract already has an `[owners]` table.

What owned paths make possible beyond context:

- The engine that says what a change affects can say which sessions a
  change concerns, so a change to forge's public names tells `workflow`.
- Two sessions working in one area show up before either submits.
- A message can be addressed to a session by name, on any account.

  `phase-audit` skill replaces the `audit` agent of the entry above. That
  leaves four kinds of thing: a session owns packages, a skill is a
  procedure any session runs, a lock guards a slot, and the queue lands
  changes.

- 2026-11-22, Willem, on the revised set: "ok, that works for this repo,
  I just want us to think about multiple people working on this, and both

- 2026-11-22, Willem, on my proposal that a desk writes a platform's

- 2026-11-22, Willem, closing open item 6: a computer in an address has
